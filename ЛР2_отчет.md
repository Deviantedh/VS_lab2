## 1. Обзор системы

Монолит из ЛР1 декомпозирован на **7 Maven-модулей** (см. [`pom.xml`](pom.xml)):

| Модуль | Порт | Тип | Стек |
| :--- | :---: | :--- | :--- |
| [`common-dto`](common-dto) | — | библиотека | Request/Response DTO, enum'ы, [`SliceResponse`](common-dto/src/main/java/portal/dto/SliceResponse.java), Swagger-аннотации |
| [`discovery-service`](discovery-service) | 8761 | инфраструктура | Netflix Eureka Server |
| [`config-service`](config-service) | 8888 | инфраструктура | Spring Cloud Config Server (native profile) |
| [`gateway-service`](gateway-service) | 8080 | инфраструктура | Spring Cloud Gateway (MVC-вариант), Springdoc OpenAPI |
| [`employee-service`](employee-service) | 8081 | бизнес-сервис | Spring Web (MVC), Spring Data JPA, Flyway |
| [`attendance-service`](attendance-service) | 8082 | бизнес-сервис | **Spring WebFlux + Reactor + Spring Data R2DBC** |

## 2. Теоретическая справка по технологиям

Краткие теоретические пояснения по технологиям, специфичным для ЛР2 (зачем нужны и как работают).

### 2.1 Netflix Eureka (Service Discovery)
**Зачем:** в микросервисной архитектуре адреса инстансов сервисов динамичны (масштабирование, перезапуски, Docker-сети). Жёстко прописывать `host:port` нельзя.
**Как работает:** [`discovery-service`](discovery-service) — Eureka Server (реестр, `register-with-eureka: false`, `fetch-registry: false`, self-preservation отключён для быстрой реакции в dev-среде). Каждый сервис — Eureka Client: при старте регистрирует себя (имя + IP + порт, `prefer-ip-address: true`) и периодически шлёт heartbeat; клиенты кэшируют реестр для lookup по логическому имени (`employee-service` → актуальные адреса инстансов). Регистрация аннотацией `@EnableDiscoveryClient` + зависимость `spring-cloud-starter-netflix-eureka-client`.

### 2.2 Spring Cloud Config Server (Centralized Configuration)
**Зачем:** единое место хранения конфигураций всех сервисов — при изменении настроек не нужно пересобирать образы; поддерживаются профили и переопределения без деплоя.
**Как работает:** [`config-service`](config-service) с `@EnableConfigServer` работает в `native`-профиле — читает yaml-файлы из каталога [`config-repo/`](config-repo) (по соглашению `<имя-сервиса>.yaml`). Клиенты подключают `spring-cloud-starter-config` и **обязаны** объявить `spring.config.import: optional:configserver:<url>` (механизм Spring Boot 2.4+): при старте сервис запрашивает у сервера свой конфиг и накладывает его поверх локального `application.yaml` (приоритет у remote). Приставка `optional:` позволяет стартовать, если Config Server временно недоступен. В docker-compose URL задаётся переменной `CONFIG_SERVICE_URL` (по умолчанию `http://config-service:8888`).

### 2.3 Spring Cloud Gateway (API Gateway)
**Зачем:** единая точка входа (Single Entry Point) — клиенты не знают адресов внутренних сервисов; шлюз решает маршрутизацию, CORS, агрегацию документации, а в перспективе — аутентификацию и rate limiting.
**Как работает:** [`gateway-service`](gateway-service) — `spring-cloud-starter-gateway-server-webmvc`. Маршруты объявлены декларативно в [`application.yaml`](gateway-service/src/main/resources/application.yaml): предикат `Path=...` + URI `lb://<service-name>`. Префикс `lb://` означает «резолвнуть имя через Eureka и балансировать нагрузку» (LoadBalancer). CORS вынесен в [`GatewayCorsConfig`](gateway-service/src/main/java/portal/gateway/GatewayCorsConfig.java) (в т.ч. `exposedHeaders: X-Total-Count` — иначе фронт не прочитает этот заголовок из браузера). Через маршруты `/v3/api-docs/{service}` + фильтр `SetPath` агрегируется Swagger.

### 2.4 OpenFeign (декларативный HTTP-клиент)
**Зачем:** вызывать REST API другого сервиса без ручного написания HTTP-кода.
**Как работает:** в [`schedule-service`](schedule-service) объявлен интерфейс [`EmployeeClient`](schedule-service/src/main/java/portal/schedule/client/EmployeeClient.java) с `@FeignClient(name = "employee-service", fallback = ...)`. Spring генерирует реализацию на лету: `@GetMapping` на методе превращается в HTTP-запрос, имя резолвится через Eureka + LoadBalancer. Активация — `@EnableFeignClients` в [`ScheduleServiceApplication`](schedule-service/src/main/java/portal/schedule/ScheduleServiceApplication.java).

### 2.5 Circuit Breaker (Resilience4j)
**Зачем:** межсервисные вызовы — самый хрупкий слой: недоступность одного сервиса может «завесить» всех его потребителей (каскадные отказы, исчерпание потоков).
**Как работает:** Circuit Breaker — автомат-предохранитель вокруг вызова. Состояния: **CLOSED** (норма; считает failures в скользящем окне), **OPEN** (при превышении порога отказов вызовы сразу отклоняются, не тратя время на таймаут), **HALF_OPEN** (пробные вызовы для проверки восстановления). Включён через `spring.cloud.openfeign.circuitbreaker.enabled: true`, параметры для инстанса `employee-service` ([schedule-service application.yaml](schedule-service/src/main/resources/application.yaml)): окно 10 вызовов, порог отказа 50%, open 10 секунд, 3 пробных вызова в half-open. Зависимость: `spring-cloud-starter-circuitbreaker-reactor-resilience4j` (реактивная интеграция с WebFlux). При срабатывании вызывается fallback — [`EmployeeClientFallback`](schedule-service/src/main/java/portal/schedule/client/EmployeeClientFallback.java), возвращающий резервный профиль вместо ошибки.

### 2.6 Project Reactor + Spring WebFlux (реактивный стек)
**Зачем:** классический стек (Spring MVC + блокирующий Tomcat) держит по потоку ОС на каждый запрос; при частых медленных I/O-операциях (внешние вызовы, БД) пулы потоков исчерпываются. Реактивный стек строит конвейер из небольшого числа event-loop потоков.
**Как работает:** Project Reactor — реализация Reactive Streams с типами **`Mono<T>`** (0..1 элемент) и **`Flux<T>`** (0..N). Данные обрабатываются ленивыми операторами (`map`, `flatMap`, `collectList`, `switchIfEmpty`); ничего не выполняется, пока нет подписки. Spring WebFlux работает на Netty: запрос обрабатывает event-loop, а блокирующая работа (если неизбежна) переносится на пул `Schedulers.boundedElastic()`. Неблокирующий контроллер возвращает `Mono<Response>` сразу, поток не ждёт результата.

### 2.7 Spring Data R2DBC (реактивный доступ к БД)
**Зачем:** JDBC — блокирующий API, который «продырявит» event-loop. Для полностью неблокирующего end-to-end пути (Netty → контроллер → БД) нужен реактивный драйвер БД.
**Как работает:** R2DBC (Reactive Relational Database Connectivity) — спецификация реактивных драйверов (аналог JDBC). [`attendance-service`](attendance-service) использует `r2dbc-postgresql` + `spring-boot-starter-data-r2dbc`: репозиторий [`ReactiveAttendanceRepository`](attendance-service/src/main/java/portal/attendance/repository/ReactiveAttendanceRepository.java) наследует `R2dbcRepository` и возвращает `Flux`/`Mono`; сущность [`ReactiveAttendanceRecord`](attendance-service/src/main/java/portal/attendance/entity/ReactiveAttendanceRecord.java) мапится аннотациями `@Table`/`@Column`/`@Id` из `org.springframework.data.relational`. Приём «ленты» — запрос `limit + 1` записей: если вернулось больше `limit`, есть следующая страница (`hasNext`), а общее количество записей не считается (это и делает ленту дешёвой — см. [`ReactiveAttendanceService.getSlice`](attendance-service/src/main/java/portal/attendance/service/ReactiveAttendanceService.java:23)).

### 2.8 Reactor + Spring Data JPA (гибрид, «мост»)
**Зачем:** требование ЛР2 — сервис на Reactor + JPA/JDBC. JPA — блокирующий API, поэтому используется паттерн **«bridge»**: блокирующий вызов заворачивается в `Mono.fromCallable(...) .subscribeOn(Schedulers.boundedElastic())`.
**Как работает:** в [`ReactiveScheduleBridgeService`](schedule-service/src/main/java/portal/schedule/service/ReactiveScheduleBridgeService.java) JPA-запросы выполняются на elastic-пуле, где блокировка потока допустима, а наружу сервис отдаёт `Mono` — API-контракт остаётся реактивным. Это компромисс: блокирующий драйвер под реактивным фасадом, но event-loop не блокируется.

### 2.9 Spring Data JPA + Flyway
**Зачем:** JPA/Hibernate — ORM-маппинг entity ↔ таблицы, декларативные запросы и транзакции (`@Transactional`). Flyway — версионирование схемы БД миграциями (`V1__`, `V2__`...), гарантирующее одинаковую схему во всех средах.
**Как работает:** репозитории наследуют `JpaRepository` (CRUD + пагинация `Pageable`/`Page`/`Slice` из коробки). Миграции лежат в [`employee-service/src/main/resources/db/migration/`](employee-service/src/main/resources/db/migration) — **employee-service выступает единственным владельцем схемы** и выполняет их при старте; остальные сервисы работают со схемой в режиме `ddl-auto: validate` (Hibernate проверяет соответствие entity и таблиц, ничего не меняя).

### 2.10 Springdoc OpenAPI (Swagger UI)
**Зачем:** живая интерактивная документация REST API, генерируемая из кода (`@Operation`, `@Tag`, `@Schema` на контроллерах и DTO).
**Как работает:** каждый бизнес-сервис отдаёт спецификацию `/v3/api-docs`; [`gateway-service`](gateway-service) агрегирует три спецификации в **один Swagger UI** (`http://localhost:8080/swagger-ui.html`) с переключателем сервисов через `springdoc.swagger-ui.urls` и маршруты-пробросы docs.

## 3. Архитектура системы

```
                [ Клиент / Frontend / Swagger UI ]
                              │ :8080
                              ▼
                   ┌────────────────────────┐
                   │    Gateway Service     │  маршруты lb:// через Eureka
                   └───────┬───────┬───────┬┘
              :8081        │  :8082│       │:8083
                   ▼       │       ▼       ▼
        ┌──────────────────┐│ ┌──────────────────┐ ┌──────────────────┐
        │ Employee Service ││ │ Attendance Svc   │ │ Schedule Service │
        │ MVC + JPA+Flyway ││ │ WebFlux + R2DBC  │ │ MVC+JPA+Reactor  │
        └────────▲─────────┘│ └──────────────────┘ └───────┬──────────┘
                 │   Feign + Circuit Breaker (Resilience4j) │
                 └──────────────────────────────────────────┘
        ┌──────────────────┐            ┌──────────────────┐
        │ Discovery (8761) │            │ Config Svc(8888) │
        │  Eureka Server   │            │  Config Server   │
        └──────────────────┘            └──────────────────┘
                              ▼
                   [ PostgreSQL :5432 portal_db ]
```

* Все сервисы — Eureka-клиенты (`@EnableDiscoveryClient`): [`EmployeeServiceApplication`](employee-service/src/main/java/portal/employee/EmployeeServiceApplication.java), [`ScheduleServiceApplication`](schedule-service/src/main/java/portal/schedule/ScheduleServiceApplication.java), [`AttendanceServiceApplication`](attendance-service/src/main/java/portal/attendance/AttendanceServiceApplication.java), [`GatewayServiceApplication`](gateway-service/src/main/java/portal/gateway/GatewayServiceApplication.java), [`ConfigServiceApplication`](config-service/src/main/java/portal/configserver/ConfigServiceApplication.java).
* Бизнес-сервисы при старте подтягивают конфигурацию из Config Server (`spring.config.import: optional:configserver:...`), а конкретные значения (БД, порты, Eureka) приходят через переменные окружения из `compose.yaml`.
* Архитектура каждого бизнес-сервиса слоистая: `controller → service → repository → entity`, DTO отделены от entity (общий модуль `common-dto`), ошибки обрабатываются `@RestControllerAdvice`.

## 4. Реализованная функциональность (требования ЛР2)

### 4.1 Eureka
Все 5 Spring-сервисов зарегистрированы в реестре `discovery-service:8761`; UI реестра: `http://localhost:8761`.

### 4.2 Config Server
`config-service:8888` (`native`-профиль, файлы из `config-repo/`). Все четыре клиентских сервиса подключены (`spring-cloud-starter-config` + `spring.config.import: optional:configserver:${CONFIG_SERVICE_URL:http://config-service:8888}`). В Docker-образ config-service каталог конфигураций копируется (`COPY config-repo /app/config-repo` в [`Dockerfile`](Dockerfile)).

### 4.3 Spring Gateway
Маршруты ([gateway-service application.yaml](gateway-service/src/main/resources/application.yaml)):

| Предикат Path | Назначение |
| :--- | :--- |
| `/api/companies/**, /api/branches/**, /api/positions/**, /api/employees/**, /api/users/**` | `lb://employee-service` |
| `/api/attendance/**` | `lb://attendance-service` |
| `/api/schedules/**, /api/shifts/**, /api/absences/**, /api/requests/**` | `lb://schedule-service` |
| `/v3/api-docs/{service}` | проброс документации (`SetPath=/v3/api-docs`) |

### 4.4 Feign Client
[`EmployeeClient`](schedule-service/src/main/java/portal/schedule/client/EmployeeClient.java): `GET /api/employees/{id}` — schedule-service проверяет существование/статус сотрудника в employee-service при операциях со сменами и заявками.

### 4.5 Circuit Breaker
Resilience4j вокруг Feign-вызовов; fallback [`EmployeeClientFallback`](schedule-service/src/main/java/portal/schedule/client/EmployeeClientFallback.java) возвращает резервный ответ при недоступности employee-service. Конфигурация инстанса: окно 10, порог 50%, open 10s, half-open 3.

### 4.6 Микросервис на Reactor + R2DBC
[`attendance-service`](attendance-service): неблокирующий цикл от Netty до PostgreSQL. Эндпоинты ([`ReactiveAttendanceController`](attendance-service/src/main/java/portal/attendance/controller/ReactiveAttendanceController.java)):

| Метод | Путь | Описание |
| :--- | :--- | :--- |
| GET | `/api/attendance` | бесконечная лента явок (Slice, `hasNext`) |
| GET | `/api/attendance/employee/{employeeId}` | лента явок сотрудника (Slice) |
| GET | `/api/attendance/{id}` | запись по ID |
| POST | `/api/attendance` | создать запись вручную (201) |
| POST | `/api/attendance/check-in` | отметка прихода (201) |
| POST | `/api/attendance/{id}/check-out` | уход + расчёт опозданий/переработок |

### 4.7 Микросервис на Reactor + JPA
[`schedule-service`](schedule-service): бизнес-логика на JPA с транзакциями, реактивный фасад через [`ReactiveScheduleBridgeService`](schedule-service/src/main/java/portal/schedule/service/ReactiveScheduleBridgeService.java) (`Mono.fromCallable` + `Schedulers.boundedElastic()`): пагинация смен по диапазону дат, поиск по ID, реактивное назначение сотрудника на смену (Feign-проверка + транзакционный сценарий `assignEmployee`).

### 4.8 Полный список бизнес-эндпоинтов (через Gateway :8080)

**employee-service** — CRUD: `/api/companies`, `/api/branches` (+ `/company/{companyId}`), `/api/positions`, `/api/users` (+ поиск по логину/сотруднику, роли); [`EmployeeController`](employee-service/src/main/java/portal/employee/controller/EmployeeController.java): пагинированный список (`page/size/sortBy`, size ≤ 50), CRUD, `POST /{id}/dismiss`, `POST /{id}/rehire`, `POST /assignments` (M2M с доп. полями), `GET /{id}/assignments`.

**schedule-service** — [`ScheduleController`](schedule-service/src/main/java/portal/schedule/controller/ScheduleController.java) (CRUD + `/branch/{branchId}`); [`ShiftController`](schedule-service/src/main/java/portal/schedule/controller/ShiftController.java) (пагинация с `X-Total-Count`/`X-Total-Pages`, `POST /{shiftId}/employees/{employeeId}`, `DELETE /{shiftId}/employees/{employeeId}`, `GET /{id}/logs`); [`AbsenceController`](schedule-service/src/main/java/portal/schedule/controller/AbsenceController.java); [`RequestController`](schedule-service/src/main/java/portal/schedule/controller/RequestController.java) (пагинация с фильтром по статусу, `POST /{id}/process`).

**Swagger:** единый UI — `http://localhost:8080/swagger-ui.html` (переключение Employee / Attendance (R2DBC) / Schedule (WebFlux + JPA)).

## 5. Доработки, внесённые в рамках данной ревизии

Ниже — точный перечень изменений, которые были внесены статически (без запуска).

### 5.1 V2-миграция: колонки опозданий/переработок (блокер attendance-service)
**Файл:** [`V2__attendance_add_late_overtime_minutes.sql`](employee-service/src/main/resources/db/migration/V2__attendance_add_late_overtime_minutes.sql) — новый.
`ALTER TABLE attendance_records ADD COLUMN IF NOT EXISTS late_minutes BIGINT` и `overtime_minutes BIGINT`. Ранее реактивная сущность мапила эти колонки, но их не было в схеме — любой `INSERT/UPDATE` в attendance-service падал бы с `column "late_minutes" does not exist`.

### 5.2 Реальное подключение к Config Server
* В `application.yaml` всех четырёх клиентских сервисов (employee, schedule, attendance, gateway) добавлен блок:
  ```yaml
  spring:
    config:
      import: optional:configserver:${CONFIG_SERVICE_URL:http://config-service:8888}
  ```
  Без `spring.config.import` конфиг-клиент в Spring Boot 2.4+ вообще не обращается к серверу — теперь при старте каждый сервис запрашивает свой конфиг (если сервер недоступен, `optional:` позволяет стартовать на локальных значениях).
* Зеркально обновлены файлы в [`config-repo/`](config-repo) (employee/schedule/attendance/gateway), чтобы remote-конфиг не расходился с локальным.
* [`Dockerfile`](Dockerfile): в рантайм-стейдж добавлено `COPY config-repo /app/config-repo` — Config Server в контейнере теперь находит свои native-локации (`file:./config-repo`).

### 5.3 Обработка ошибок в attendance-service (WebFlux)
Новые классы в [`portal/attendance/exception`](attendance-service/src/main/java/portal/attendance/exception):
* [`GlobalExceptionHandler`](attendance-service/src/main/java/portal/attendance/exception/GlobalExceptionHandler.java) — `@RestControllerAdvice` для WebFlux: `ResourceNotFoundException` → 404, ошибки валидации параметров/тела (`HandlerMethodValidationException`, `WebExchangeBindException`, `ServerWebInputException`) → 400, всё остальное → 500 с человекочитаемым телом (лог с ошибкой остаётся на сервере);
* [`ErrorResponse`](attendance-service/src/main/java/portal/attendance/exception/ErrorResponse.java) — формат тела ошибки (timestamp, status, error, message) — в том же стиле, что в MVC-сервисах;
* [`ResourceNotFoundException`](attendance-service/src/main/java/portal/attendance/exception/ResourceNotFoundException.java).

Дополнительно: в [`ReactiveAttendanceService.checkOut`](attendance-service/src/main/java/portal/attendance/service/ReactiveAttendanceService.java) «запись не найдена» теперь бросает `ResourceNotFoundException` (было `IllegalArgumentException` → голый 500), и контроллер отдаёт корректный 404.

### 5.4 Валидация пагинации в attendance-service
[`ReactiveAttendanceController`](attendance-service/src/main/java/portal/attendance/controller/ReactiveAttendanceController.java): класс помечен `@Validated`, параметры `page`/`size` аннотированы `@Min(0)` / `@Min(1) @Max(50)`. Раньше отрицательная страница приводила к `IllegalArgumentException` из `PageRequest.of` (500), а размер не был ограничен на уровне API.

### 5.5 Явная сортировка бесконечной ленты
[`ReactiveAttendanceService.getSlice`](attendance-service/src/main/java/portal/attendance/service/ReactiveAttendanceService.java:23): `PageRequest.of(page, fetchSize, Sort.by(DESC, "id"))`. Без `Sort` порядок страниц не гарантирован БД — при листании возможны дубли/пропуски записей.

### 5.6 Реализация реактивного назначения на смену
[`ReactiveScheduleBridgeService.assignEmployeeToShiftReactive`](schedule-service/src/main/java/portal/schedule/service/ReactiveScheduleBridgeService.java:49) был заглушкой (вызывал Feign и просто возвращал смену, ничего не сохраняя). Теперь метод: (1) проверяет сотрудника в employee-service через Feign + Circuit Breaker; (2) делегирует в транзакционный [`ShiftService.assignEmployee`](schedule-service/src/main/java/portal/schedule/service/ShiftService.java:77) (проверки отпусков/пересечений, Many-to-Many, аудит-лог) внутри `Mono.fromCallable` на `boundedElastic`.

### 5.7 ddl-auto → validate, единый владелец схемы
В `employee-service` и `schedule-service` (и их копиях в `config-repo`) `spring.jpa.hibernate.ddl-auto` изменён с `update` на `validate`: Hibernate только сверяет entity со схемой, схему меняет исключительно Flyway в сервисе-владельце (employee-service). Это устраняет риск, когда два сервиса «соревновались», изменяя одну и ту же схему.

## 6. База данных и схема

Схема создаётся миграциями Flyway в сервисе-владельце: [`V1__init_schema.sql`](employee-service/src/main/resources/db/migration/V1__init_schema.sql) (14 таблиц + индексы под пагинацию) и [`V2__attendance_add_late_overtime_minutes.sql`](employee-service/src/main/resources/db/migration/V2__attendance_add_late_overtime_minutes.sql).

**Типы связей (требование ЛР1):**
* One-to-Many / Many-to-One: `companies → branches`, `schedules → shifts`, `users → roles`;
* Many-to-Many (чистая): `shift_employees` (смены ↔ сотрудники, `UNIQUE(shift_id, employee_id)`);
* Many-to-Many с доп. полем: `employee_assignments` (сотрудник ↔ филиал/должность + `started_at`, `ended_at`, `is_primary`).

**Enum'ы** во всех таблицах хранятся как `VARCHAR` (`status`, `type`, `code`, `action`) и мапятся через `@Enumerated(EnumType.STRING)` — сериализация в БД строками.

**Пагинация:**
* обычная — `Pageable` на всех списках, лимит 50 enforced (`@Max(50)` на контроллерах);
* **бесконечная прокрутка** — [`SliceResponse`](common-dto/src/main/java/portal/dto/SliceResponse.java) (`content`, `pageNumber`, `pageSize`, `hasNext`, без общего количества) в attendance-service;
* **пагинация с общим количеством в хедере** — `ShiftController`: `X-Total-Count`, `X-Total-Pages` (заголовок пробрасывается CORS-конфигом шлюза).

**Транзакционные сценарии (с обоснованием):**
1. [`ShiftService.assignEmployee`](schedule-service/src/main/java/portal/schedule/service/ShiftService.java:77) — назначение на смену: проверки (статус, отсутствие/отпуск, пересечения смен) + запись в Many-to-Many + аудит-лог. Транзакция обязательна, т.к. изменяются несколько таблиц: без атомарности сбой оставил бы «смену без аудита» — нарушение инварианта «каждое изменение состава логируется».
2. [`RequestService.processRequest`](schedule-service/src/main/java/portal/schedule/service/RequestService.java:97) — обработка заявки на отпуск: смена статуса заявки + фиксация `employee_absences` + автоснятие сотрудника с пересекающихся смен с аудитом. Частично обработанная заявка («одобрена, но смены не сняты») давала бы конфликтующие данные — поэтому всё в одной транзакции.
3. Дополнительно: [`ShiftService.removeEmployee`](schedule-service/src/main/java/portal/schedule/service/ShiftService.java:133), каскадное удаление смен с attendance-записями.

**Конфигурация через окружение:** `${DB_URL}`, `${DB_USER}`, `${DB_PASSWORD}`, `${R2DBC_URL}`, `${SERVER_PORT}`, `${EUREKA_CLIENT_SERVICEURL_DEFAULTZONE}`, `${CONFIG_SERVICE_URL}` — задаются в `environment:` сервиса в [`compose.yaml`](compose.yaml).

## 8. Проблемы и недоделки

> Раздел — по результатам статического анализа; часть пунктов закрыта доработками §5 (отмечено).

### Критичные
1. ~~Config Server фактически не использовался~~ — **закрыто §5.2** (добавлен `spring.config.import`, `config-repo` копируется в образ). Остаточный нюанс: если Config Server временно недоступен, сервисы стартуют на локальных конфигах (`optional:`) — для прод-стиля стоит переключить на обязательный импорт.
2. ~~Колонки `late_minutes`/`overtime_minutes` отсутствовали в БД~~ — **закрыто §5.1** (V2-миграция). Нюанс: миграцию выполняет только employee-service — attendance-service зависит от порядка старта (в compose employee-service стартует раньше, БД общая).
3. **Тесты отсутствуют полностью.** В проекте нет ни одного `src/test`, не подключён `spring-boot-starter-test` — требования ЛР1 (покрытие ≥ 70%, Testcontainers + JUnit Jupiter) не выполнены. Рекомендуемый минимум: интеграционные тесты транзакционных сценариев `assignEmployee`/`processRequest` на Testcontainers PostgreSQL, реактивные тесты attendance-service (`StepVerifier`), тест Circuit Breaker (падение employee-service → fallback).

### Средние
4. ~~Нет обработчика ошибок в attendance-service~~ — **закрыто §5.3**.
5. ~~Нет валидации `page/size` в attendance-service~~ — **закрыто §5.4**.
6. **Модель «общая БД на всех» + дублирование сущностей.** `employee-service` и `schedule-service` держат по 13 одинаковых JPA-сущностей над одной схемой. Это нарушает принцип «database per service»: изменение модели в одном сервисе может сломать второй (`ddl-auto: validate` теперь хотя бы упадёт с внятной ошибкой, а не молча разойдётся). Долгосрочно — вынести расписание в собственную схему/БД.
7. **Fallback возвращает правдоподобные фиктивные данные** ([`EmployeeClientFallback`](schedule-service/src/main/java/portal/schedule/client/EmployeeClientFallback.java), статус `ACTIVE`) — при разборе инцидентов легко перепутать с реальным ответом; лучше помечать degraded-ответ явно.
8. **Нестабильность при рестарте Config Server**: конфиг сервисов не обновляется динамически (нет `@RefreshScope`/Spring Cloud Bus) — изменение `config-repo` требует рестарта сервиса.

### Мелкие
9. `Dockerfile`: `EXPOSE 8080` захардкожен при параметризуемом `SERVER_PORT`; нет шага кэширования зависимостей Maven (каждая сборка скачивает всё заново); сборка всегда `-DskipTests`.
10. ~~В compose `depends_on` бизнес-сервисов на discovery — только `service_started`~~ — **закрыто в §9.1** (внедрены healthcheck'и и цепочка `service_healthy`: discovery → config → бизнес-сервисы).
11. Дефолтные креды БД (`portal_secret`) прописаны в yaml — для учебного проекта допустимо, но секреты лучше держать только в env.
12. Frontend (`frontend/`) не включён в `compose.yaml` — запускается отдельно.
13. `ReactiveScheduleBridgeService.toDto` возвращает пустой список `assignedEmployees` — упрощение, не влияющее на логику назначения.

## 9. Отладка запуска: найденные проблемы и их решения (простым языком)

> Этот раздел — хронология реальной отладки запуска системы через `docker compose up`: какие проблемы возникали, почему и как их исправили. Все пункты проверены на живой системе.

### 9.1 Сервисы стартовали раньше инфраструктуры (гонки запуска)

**Симптом:** в логах employee/schedule/attendance/gateway при старте — `Connection refused` к `http://config-service:8888`, а config-service в свою очередь не мог достучаться до Eureka.

**Причина:** в [`compose.yaml`](compose.yaml) бизнес-сервисы зависели только от postgres и «запущенного» discovery. Docker считает контейнер запущенным сразу после старта процесса — а JVM внутри ещё минуту-две «греется». Сервисы стартовали раньше, чем Config Server и Eureka реально начали принимать запросы.

**Решение:**
* для `discovery-service` и `config-service` добавлены **healthcheck'и** (проверка реального HTTP-ответа через busybox `wget`, с запасом `start_period: 600s` — JVM под нагрузкой стартует до 4–5 минут);
* все зависимые сервисы переведены на `depends_on: condition: service_healthy` — выстроилась цепочка: **postgres → discovery → config → gateway/employee/attendance/schedule**.

**Результат:** порядок старта стал детерминированным, «Connection refused» при старте исчезли.

### 9.2 Config Server «душил сам себя» (бесконечная рекурсия)

**Симптом:** контейнер `portal-config` помечался `unhealthy`; в логах — сотни `Read timed out` на GET `/attendance-service/default`, а Tomcat-потоки исчерпаны (`o-8888-exec-177…199` — весь пул из 200).

**Причина:** в файлах [`config-repo/*.yaml`](config-repo) (их отдаёт Config Server клиентам) был прописан `spring.config.import: configserver:http://config-service:8888`. Обрабатывая запрос клиента, Config Server «видел» в отдаваемом конфиге импорт **на самого себя** и порождал новый запрос к себе с того же потока — рекурсия до исчерпания пула потоков. Healthcheck не мог получить ответ за 5 секунд → контейнер считался нездоровым.

**Решение:** `spring.config.import` удалён из всех четырёх файлов `config-repo` — этот импорт нужен **только** в собственном `application.yaml` каждого сервиса (там он и остался). Config Server отдаёт конфиг, но сам никуда за ним не ходит.

### 9.3 employee-service и schedule-service падали при старте: «Not a managed type»

**Симптом:** контейнеры перезапускались по кругу (`Restarting (1)`), в логах — `Not a managed type: class portal.entity.Branch`, API на :8081/:8083 не отвечали (отсюда 404 у клиентов).

**Причина:** при декомпозиции сущности вынесли в общий пакет `portal.entity`, а классы приложений лежат в `portal.employee` / `portal.schedule`. `@SpringBootApplication` сканирует только свой пакет и ниже — JPA не находил сущности, и создание репозиториев падало.

**Решение:** в оба класса приложений добавлена аннотация `@EntityScan(basePackages = "portal.entity")`. Нюанс Spring Boot 4: аннотация переехала из `org.springframework.boot.autoconfigure.domain` в **`org.springframework.boot.persistence.autoconfigure`** — старый импорт не компилируется.

**Файлы:** [`EmployeeServiceApplication`](employee-service/src/main/java/portal/employee/EmployeeServiceApplication.java), [`ScheduleServiceApplication`](schedule-service/src/main/java/portal/schedule/ScheduleServiceApplication.java).

### 9.4 Gateway отдавал 404 на все маршруты

**Симптом:** шлюз жив (`/actuator/health` → UP), но любой бизнес-запрос (`/api/companies` и т.д.) → 404.

**Причина:** в Spring Cloud Gateway 5.0 (MVC-вариант) свойства маршрутов читаются из префикса **`spring.cloud.gateway.server.webmvc.routes`**, а в проекте использовался `spring.cloud.gateway.server.mvc.routes` — такой префикс молча игнорируется, маршрутов ноль. Проверено по `spring-configuration-metadata.json` из jar'а `spring-cloud-gateway-server-webmvc-5.0.3`.

**Решение:** префикс исправлен в [`gateway-service/src/main/resources/application.yaml`](gateway-service/src/main/resources/application.yaml) и [`config-repo/gateway-service.yaml`](config-repo/gateway-service.yaml).

### 9.5 Swagger через gateway: «Failed to fetch» / CORS

**Симптом:** Swagger UI открывался, но запросы из него падали с `Failed to fetch. Possible reasons: CORS...`; у employee — 500. Прямые вызовы API работали.

**Причина:** OpenAPI-спецификация, отданная через gateway, содержала `servers: http://172.18.0.x:8081..8083` — **внутренние Docker-адреса сервисов** (gateway подменяет Host на адрес цели, и springdoc генерирует URL по этому Host). Браузер пытался стучаться напрямую в контейнерную сеть — откуда она недоступна.

**Решение (две части):**
1. Gateway стал прокидывать `X-Forwarded-Host/Proto/Port`:
   ```yaml
   spring.cloud.gateway.server.webmvc:
     trusted-proxies: ".*"                      # в SCG 5.0 X-Forwarded работает только для доверенных прокси
     x-forwarded-request-headers-filter:
       enabled: true
       host-enabled: true, port-enabled: true, proto-enabled: true
       for-append/host-append/port-append/proto-append: false
   ```
2. Сервисы стали учитывать эти заголовки: `server.forward-headers-strategy: framework` в application.yaml employee/schedule/attendance.

**Результат:** в docs теперь `servers: http://localhost:8080` — все запросы из Swagger идут через шлюз (same-origin, без CORS).

### 9.6 Эндпоинт для проверки Circuit Breaker

Feign-вызов employee-service существовал только внутри [`ReactiveScheduleBridgeService`](schedule-service/src/main/java/portal/schedule/service/ReactiveScheduleBridgeService.java), но **не был доступен ни через один REST-эндпоинт** — Circuit Breaker негде было продемонстрировать. В [`ShiftController`](schedule-service/src/main/java/portal/schedule/controller/ShiftController.java:142) добавлен:

```
POST /api/shifts/reactive/{shiftId}/employees/{employeeId}
```

(реактивный Mono-контроллер: Feign-проверка сотрудника под Circuit Breaker → транзакционное назначение на смену). Сценарий демонстрации и результаты — в разделе 10.

### 9.7 Итог: как теперь выглядит успешный запуск

```
docker compose up -d --build
```
1. postgres → healthy (pg_isready);
2. discovery → healthy (GET /eureka/apps отвечает 200);
3. config → healthy (GET /attendance-service/default отвечает 200 — реальная отдача конфига);
4. gateway, employee, attendance, schedule — стартуют только после этого, подтягивают конфиг из Config Server и регистрируются в Eureka;
5. `docker compose ps` — все контейнеры `Up ... (healthy)`, в логах нет `Connection refused`.

## 10. Демонстрация Circuit Breaker — сценарий и результаты

**Подготовка:** создать через Swagger тестовые данные: компанию → филиал → сотрудника (employee-service) → расписание → смену (schedule-service).

**Сценарий (два терминала):**

Терминал A — поток логов schedule-service:
```
docker logs -f portal-schedule-service
```

Терминал B — запросы:
```
:: 1. штатное назначение (employee-service работает)
curl -X POST "http://localhost:8080/api/shifts/reactive/1/employees/1"

:: 2. «отказ» employee-service
docker stop portal-employee-service

:: 3. повторное назначение — ответ приходит мгновенно из fallback
curl -X POST "http://localhost:8080/api/shifts/reactive/1/employees/1"

:: 4. восстановление
docker start portal-employee-service
```

**Замеренные результаты реального прогона:**

| Сценарий | Время ответа | Статус |
| :--- | :---: | :---: |
| Назначение при работающем employee-service | 0.13 с | 200 |
| Назначение при **остановленном** employee-service (fallback) | **0.03 с** | 200 |
| Повторные вызовы при отказе (Circuit Breaker открыт) | 0.02 с | 409 «уже назначен» — быстро, без зависания |
| Отзывчивость шлюза на другие запросы во время отказа | 0.009 с | — |
| Восстановление после `docker start` | 0.26 с | 200 |

В логах терминала A при этом появляются строки:
```
WARN ... FeignBlockingLoadBalancerClient : Load balancer does not contain an instance for the service employee-service
```
— Feign мгновенно фиксирует отказ, Resilience4j переключает на [`EmployeeClientFallback`](schedule-service/src/main/java/portal/schedule/client/EmployeeClientFallback.java), транзакция назначения завершается штатно; ни один запрос не «висит», каскадного отказа нет. Именно это и требуется показать по заданию.
